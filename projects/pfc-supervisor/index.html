Overview

The AI server did not need to stay awake when no work was running.

The problem, my contribution, and the constraint that shaped the work.

Context

The problem I was solving

The B70 compute server is useful when AI, Minecraft, print-control, or scheduled jobs need it, but leaving the full system awake all day wastes power. A basic timer was not enough because the work is irregular and some jobs must wake the server before they run.

System

What I built

PFC splits responsibility between the main server and a low-power Pi. The Pi keeps the control surface, Hermes schedule cache, wake protections, policy checks, and retained history available even when the main server is asleep.

Ownership

My role

I designed the operating model, dashboard, power policy, runtime reconciliation, schedule-cache visibility, eligibility matrix, release process, and recovery behavior. The project is still evolving as I add better attribution, notifications, and cross-system checks.

Safeguard

The safety rule

Automatic suspend fails safe. If telemetry is stale, a protected job is near, an inhibition lease is active, a workload is unknown, or a required runtime state cannot be verified, PFC blocks sleep and explains why.

Design decisions

Automatic sleep only works when the safety logic is visible.

The tradeoffs and safeguards I used to move the project forward.

01

Keep the Pi awake, not the whole server

The low-power controller retains the minimum services needed for schedules, wake dispatch, status, and operator access while the high-power node sleeps.

02

Make every sleep decision inspectable

The eligibility matrix shows each rule as eligible, blocked, unknown, or stale, plus the subsystem that supplied the decision.

03

Protect scheduled work before it starts

Hermes jobs are cached with a wake-dispatch window and protected-until window so the server can wake before execution instead of after a job is already late.

04

Separate estimates from direct measurement

The energy ledger labels baseline-based estimates and keeps coverage visible. A direct meter source is the next step for stronger attribution.

What the number means

Useful estimate, visible caveat

PFC currently attributes most host energy from configured wattage baselines and observed state history. The dashboard deliberately keeps that limitation next to the savings claim.

  • Observed sleep is retained from real state history.
  • Avoided energy is estimated against an always-on baseline.
  • The Pi’s own energy use is included in the combined projection.
  • Direct metering is the planned accuracy upgrade.

Results

Lower idle power without giving up schedules or recovery.

The result, the main lesson, and the next useful improvement.

01 · Outcome

Useful sleep instead of blind shutdown

The server can stay off during genuine idle time without giving up scheduled jobs or operator visibility.

02 · Outcome

Power savings with context

The dashboard ties savings to observed sleep and configured baselines, while keeping estimation limits visible.

03 · Outcome

Safer automation

A blocked suspend is treated as a successful safety decision, not a failure to automate.

What comes next

The next useful improvement is already clear.

The highest-value next step is direct metering for the PFP host. That will replace more modeled attribution with measured wall-power data and make the savings ledger more defensible over longer periods.
