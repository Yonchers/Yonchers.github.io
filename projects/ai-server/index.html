Overview

I built the B70 around the local AI work I actually wanted to run.

The problem, my contribution, and the constraint that shaped the work.

Context

The problem I was solving

I wanted a private system that could run useful models locally, support long contexts, host engineering tools, and remain under my control. A benchmark-only build was not enough; the machine needed to become dependable infrastructure.

System

What I built

The B70 is a custom server, model host, application platform, and test bench. It runs llama.cpp services, stores model configurations, exposes local endpoints, hosts dashboards, and supports the printer and power-control projects.

Method

How I evaluate models

I compare models by role instead of using one general score. Manager tests cover scope discipline, delegation, recovery, preservation, and verification. Worker tests cover coding, shell/tool use, implementation accuracy, debugging, and throughput.

Iteration

What changed over time

I retired the 122B model after proving that it could run because it was too large and impractical for the hardware. That decision is part of the engineering evidence: the best configuration is the one that remains useful in the real workflow.

Design decisions

A useful local model is more than a single speed number.

The tradeoffs and safeguards I used to move the project forward.

01

Benchmark on the actual machine

Generation and prompt-processing measurements come from the B70 configuration rather than internet averages or vendor specifications.

02

Separate manager and worker roles

A model that plans well may not be the best model for shell work or coding. I test replacement potential against the job it would actually perform.

03

Keep launch settings reproducible

Model recommendations include the full context, GPU-layer, cache, and server launch settings so a result can be repeated.

04

Retire impractical configurations

The 122B stress test remains documented, but it is excluded from the active stack because the cost in memory and usability was not justified.

Results

A private AI platform that now supports several other projects.

The result, the main lesson, and the next useful improvement.

01 · Outcome

A practical active stack

Fast MoE models provide a better balance of capability, generation speed, and memory use than the retired oversized configuration.

02 · Outcome

Infrastructure for other projects

The server now supports AI runtimes, dashboards, automation, model evaluation, and local development workflows.

03 · Outcome

A repeatable test process

Configurations and results can be compared over time as runtimes, models, and application roles change.

What comes next

The next useful improvement is already clear.

The next phase is deeper task-based evaluation against Muse and Qwen3.6, plus more automated capture of quality, recovery, and throughput across manager and worker roles.
